# Testing

**Status:** draft 0.1, 2026-11-24. Hardened: pass 1 (2026-11-25), pass 2 (2026-11-25), pass 3 (2026-11-25), planning findings (2026-11-25).

How circitor is tested without touching GitHub, and what the owner checks by hand.

## Rules

- **TST-1** **No automated test contacts GitHub**, or any host but the loopback. **A test build** has the `test-endpoint` feature: its GitHub client takes its address from `CIRCITOR_TEST_GITHUB` and refuses any host but the loopback, `exit_after` goes down to 1 s, `CIRCITOR_TEST_VERSION` replaces the version it reports, `CIRCITOR_TEST_CLI_LIMIT` replaces CLI-7's 90 s, and `CIRCITOR_TEST_STOP_DELAY` holds its stop that many seconds. Its GitHub client sends its process ID in an `x-circitor-test-pid` header. `CIRCITOR_TEST_GITHUB` is a full `http://127.0.0.1:<port>/graphql` URL; without it, or with another host, a test build stops at start, naming it. The real-process tests declare `required-features = ["test-endpoint"]`, and CI runs `cargo test --features test-endpoint`. The release build has none of this. Live measurements are a separate, manual activity with their own rules ([docs/05](../docs/05-measurements.md)).
- **TST-2** **Deterministic:** all time comes from the clock (TST-4), randomness is seeded, and no test sleeps on the wall clock except those that start real processes (TST-9).

## Test doubles

- **TST-3** **The fake GitHub** is an HTTP server on the loopback that answers circitor's GraphQL queries from a scripted world: PRs with their fields, checks, comments and reviews, each changing at scripted times on its own clock. That clock is GitHub's: it moves forward with every advance and every sleep, by as much as the wall time, and never back. Setting the local wall time back leaves it where it is, and a test can set the two apart by a fixed skew. Lists are paged by cursor over the world as it is at each request, so a change between two pages shifts them.
  - It answers the queries circitor sends (POL-4, POL-6, POL-8, POL-12, POL-16), with a `rateLimit` block whose cost is GitHub's formula (docs/02 §2, documented): a test checks it gives each row of the measured table its measured cost. Each answer has a `Date` header, from its own clock, which a test can leave out, and `x-ratelimit-*` headers (MOD-6, POL-25), and a test can change `viewer.login` (MOD-11).
  - **By default its world behaves as docs/02 §4 records:** the rollup `null` with no checks and `FAILURE` while others run; `updatedAt` moved by a push, a comment, a draft change, a close or a merge, never by a check; a merged PR's `mergeable` `UNKNOWN`.
  - It can be told to misbehave: a 5xx, a hang, a dropped connection, a 401, a partial error with `NOT_FOUND` for one node, an error inside a PR's node (POL-21, POL-24), a 200 without `data`, a 200 whose body isn't JSON or is cut short, a redirect, a refused connection, an exhausted rate limit, a secondary limit with and without `Retry-After`, `mergeable` unknown for a number of reads, the old head served for a while after a push, and a check read out of order. Its exhausted and secondary-limit answers follow POL-25 and are assumed (docs/02 §6 item 6).
  - **It parses each query and checks it against GitHub's public GraphQL schema** (`https://docs.github.com/public/fpt/schema.docs.graphql`, fetched without a token and refreshed by hand), kept in `testdata/github/schema.graphql`: a field the schema lacks fails the test. It answers only the fields asked, and costs the query from its connections. The cost test's queries are in `tests/cost/`, one per row of the measured table, `frag.graphql` among them.
  - **The test sets `remaining` and the reset time** apart from circitor's spending, to play other tools on the same token, and can make them lag (docs/02 §2).
  - **It fails the test if it receives a mutation** (POL-1), a request while another is in flight, or one less than 1 s after the last ended, on the test clock's monotonic time (POL-2). A request ends when it's answered or its connection closes; a hung answer watches its connection. These checks are per daemon: they start afresh at each start or restart, and in TST-9 hold per process, told apart by the `x-circitor-test-pid` header (TST-1).
  - It records every request with its time, its cost and the node IDs it asked for, for the quota tests (TST-6).
- **TST-4** **The clock** is a trait with a wall time and a monotonic time, kept apart. The test clock is advanced by the test. **An advance fires each timer at its own due time, in order**, and settles after each before time moves on. **Settled** means the daemon's count of work in flight, which a test build keeps, is 0 (requests to GitHub not held by a scripted hang, API requests being answered other than held waiters, and timers due now), and the fake has answered, closed or is holding by script every connection it accepted. Timers due at the same instant fire in the order they were set. The clock never moves by itself. A sleep moves time in one step: the wall time alone, or both clocks, as a platform whose monotonic clock counts a suspend would (POL-22, docs/04 §8 item 6). The wall time can also be set back alone. **Every timeout circitor sets runs on it**, POL-2's 20 s, OPS-5's 10 s and the CLI's limits (CLI-7) included, so the fake GitHub's hang costs no wall time. Only TST-9's real processes wait on the wall clock (TST-2).
- **TST-5** **The harness** starts the daemon in-process with the test clock, the fake GitHub, a fake token source that gives a token, no login, a failure, or is slow up to its 10 s limit (OPS-5), and temporary directories, and can stop, crash (drop it without OPS-7's stop) and restart it on the same directories. The CLI's commands run against it as functions, with their output and exit code captured.
  - **Unless a test says otherwise,** the daemon runs `spawned` with OPS-2's defaults but `exit_after` 0, writes its log to a buffer the test reads, and is given its state directory and socket path under `/tmp` directly, not through `HOME`, so the socket path stays under 103 bytes on macOS. A test of OPS-8 sets `exit_after` itself. The harness gives the daemon a fixed random seed, and the test clock starts at 2026-11-24T22:00:00Z.
  - **Each command takes its inputs** (CLI-13): the test clock, a fixed time zone (UTC), a working directory and environment, a version, and a fake spawner. The fake spawner starts the in-process daemon, or exits 1 with an OPS-1 message, or exits 0, or never binds.
  - The harness can make a temporary git repository with an `origin` and a current branch, and give the daemon another version or `mode` than the CLI: a newer, a `foreground` and an unparsable one are kept, with a warning (CLI-9).

## What is tested

- **TST-6** **Quota.** The figures are for OPS-2's defaults; with other values they scale as POL-13 and POL-14 say. In a world where nothing changes and `mergeable` is known, with 10 tracked PRs:
  - an hour in the active tier costs at most 130 points; an hour idle at most 15; and at least 110 polls are sent in the active hour and 11 in the idle
  - one hot PR adds at most 250 points an hour in the active tier (POL-14). In the idle tier it adds at most 350 an hour's rate, measured over the idle part of one 3 600 s wait: a wait's arrival keeps the tier active for `idle_after`.
  - one waited-on PR is refreshed at least 230 times in the active hour, each about 10 s after its last refresh of any kind; a `show` of a `checks_pending` PR makes it hot for 2 minutes, of a `ready` one doesn't; a merged or `asked` PR is asked for once per `idle_interval` (POL-10, POL-14)
  - above 80 % of `quota.max_per_hour`, `interval` and `hot_interval` double; at 100 %, only forced refreshes, reading through, `track` and their POL-12 requests are sent, in 30 s windows (POL-23)
  - with 200 tracked PRs, the active tier runs `slowed` or `capped` as STA-3 says, and an hour costs at most 600 points
  - each state's `daemon.problem`, and `auth` over `quota_low` when both hold; `quota_capped` and `quota_reserve` raised together and cleared each on its own condition (API-4, API-5)
  - with `remaining` under the reserve, polls and hot refreshes run every `idle_interval`; with both the reserve and the cap, none run (POL-23)
  - exhausted: nothing is sent until `x-ratelimit-reset`; a tracked PR is answered from memory, a read-through gets `rate_limited` with `until`, exit 9. A secondary limit: nothing until `Retry-After`, or 60 s doubling without one (POL-23, POL-25). Also an answer without `x-ratelimit-reset` (an hour), a secondary limit as a 403 and as a 200 with an error, and a wall-clock jump past the reset, which resumes sending
- **TST-7** **Golden output.** The text of `list`, `show`, `changes`, `wait`, `status`, `refresh` and `stop`, every outcome line of CLI-6, `more events:`, and every error line, is compared with files in `tests/golden/`, rewritten only with `CIRCITOR_UPDATE_GOLDEN=1`. Before comparing, the temporary root is replaced by `<tmp>` and an OS error's text by `<os error>`. Each exit code of CLI-5 has a test; 130 and 143 are TST-9's. `--json` output too, with every API-19 key present when empty; an unknown parameter and a `timeout` of 3 601 get `bad_request` (API-1, API-12).
- **TST-8** **Scenarios**, each a scripted world run on the test clock. The timings come from the logs in `docs/measurements/`. **Where a row and the requirement it cites differ, the requirement wins.** A row's values are OPS-2's defaults and the other values in force today.

| `push-old-head` | After a push, GitHub serves the old head with its green result for 3 s. `wait --until checks-done --sha <new>` doesn't hold until the new head's checks finish (API-10). Without `--sha` it holds at once: documented behaviour. |
| `no-ci` | A PR with no checks ever becomes `ready` at the first refresh sent 60 s after the settle start (MOD-6), and `checks-done` holds with `none`. Between refreshes it stays `checks_pending` (MOD-6). |
| `first-check-early` | One commit status passes at +3 s and the workflow's checks appear at +8 s. `status` stays `checks_pending`, and `checks-done` doesn't hold on the first read (MOD-6, MOD-11). |
| `late-ci` | A new head, or a new PR, has no checks for 6 s (measured) and for 40 s. `status` stays `checks_pending`, not `ready`, and `checks-done` doesn't hold until they appear (MOD-6, MOD-11). |
| `one-fails-others-run` | One check fails while another runs for 78 s. `checks.state` stays `pending` with `failed: 1`; `checks-done` holds only when the last finishes, and the CLI exits 8 (MOD-5, CLI-5). |
| `skipped-and-cancelled` | A skipped check passes; a cancelled one fails (MOD-5). |
| `commit-status` | A commit status goes pending, then failure, in the same list as check runs (MOD-3). Posted again as pending, it reads `in_progress` again (MOD-4). |
| `check-out-of-order` | A check run read as running and then as queued makes no event, and `checks.state` stays `pending` (MOD-4, MOD-14). |
| `merged` | A PR leaves the open list; the refresh by ID shows `merged`; `wait --until merged` is satisfied, a `checks-done` wait ends with `merged` (POL-10, API-11). |
| `closed` | The same with `closed`: a `merged` wait, and a `checks-done` wait whose checks aren't done, end with `closed`, exit code 4; a `changed` wait is satisfied, exit code 0 (API-11). |
| `reopened` | A closed PR is open again at the next poll, and its retention clock is cleared (POL-10, STA-2). Its `status` reads `checks_pending` until settled (MOD-6). |
| `settled-at-once` | A PR with passing checks whose `updatedAt` is 2 minutes old is `ready` at its first refresh, also after a restart. With `updatedAt` 10 s old, or with no `Date` header, it reads `checks_pending` until a refresh sent 20 s later (MOD-6). With the local clock 5 minutes behind GitHub's, a PR 10 s old by `Date` still reads `checks_pending`. |
| `mergeable-unknown` | `UNKNOWN` on an unchanged head within 60 s of the last read of `yes` makes no event and the record keeps `yes`; an `UNKNOWN` read later than that, or the first read after a sleep longer than 60 s, reads `unknown` (MOD-8). After a push the record reads `unknown`, then the new value, each a visible change; the follow-up read happens after 3 s (MOD-8, POL-11). With a waiter and `UNKNOWN` for 20 reads, each refresh reading `UNKNOWN` gets at most one follow-up, and a follow-up never another; at start, every PR reading `UNKNOWN` shares one follow-up request; capped or in reserve, none is sent (POL-11, POL-23). |
| `conflict` | `CONFLICTING` gives `status: conflict` (MOD-11, docs/02 §4). |
| `new-review` | A count rises; one extra request fetches IDs; one `activity` event carries the review with its fetch path; a thread reply arrives as a review with `inline: 1` (POL-12, MOD-12). |
| `baseline` | A PR tracked with 5 existing comments makes no `activity` events (STA-5). |
| `read-through` | A PR created a second ago and never polled is answered, not "not found" (POL-16). |
| `cursor-reset` | A cursor from before a restart, and one older than the history, give `reset: true` and the full state (STA-9). |
| `many-checks` | 187 checks are read over two pages; 400 give `truncated` (POL-8, MOD-7). 100 checks are one page, 101 two; 300 aren't truncated, 301 are; a failed second page leaves the record as it was, and `stale` (POL-8). With 400 checks and the 300 read all passed, a rollup of `PENDING` reads `pending`, `SUCCESS` `passing`, `FAILURE` `failing`, where `checks-done` exits 8 with `(truncated: unread checks may still run)` (MOD-7, CLI-6). |
| `tiers` | Active to idle after `idle_after`; a request wakes it and polls at once; a waiter makes one PR hot (POL-13, POL-14). |
| `github-down` | 5xx for 10 minutes: records go stale and are still served, the backoff reaches 5 min, one log line at each end, waiters survive (POL-19). The same for a hang (abandoned at 20 s), a refused connection, a body that isn't JSON, and a redirect, which isn't followed (OPS-16). A read-through during the backoff is sent at most once per step (POL-16). |
| `token-rotated` | A 401, the token is read again, the retry succeeds. Then a token that stays bad: tracked PRs are answered from memory with `problem: auth`, and a read-through gets the `auth` error (POL-20). |
| `repo-gone` | `NOT_FOUND` for one PR on every refresh for 5 minutes, at least three of them, makes it `gone`; three in under 5 minutes leave it open and `stale`. With a changed login, or every tracked PR `NOT_FOUND` in one poll of two or more, it never becomes gone. A lone tracked PR becomes gone; a hot refresh's `NOT_FOUND` neither counts nor breaks the run. The other PRs are unaffected (POL-21, MOD-11). |
| `sleep` | The wall clock jumps 2 hours: records are stale, a poll starts, and a wait past its deadline ends as `timeout` (POL-22). Run both ways (TST-4). Where the monotonic clock counts the suspend, no sleep is noticed (POL-22) and the same outcomes follow from the clocks alone; only the wall-only run logs the sleep. On waking one poll is sent, never one per missed interval. A PR merged during the sleep reads `merged` after the poll on waking. |
| `owners` | Only PRs of the configured owners are tracked; a manual one from another owner still is (POL-5, STA-1). |
| `bare-pr` | A PR opened after the last poll is found after one forced poll; after a `shared` poll, one already in memory is still found; of a merged and a closed PR on the branch, the later `closed_at` wins; two open matches exit 2, listing both; outside a git repository, exit 2 with no request sent (CLI-2). |
| `restart` | A PR saved open merges and gets 2 comments while no daemon runs. After a restart, `list` names it in `pending` until its first refresh; a `wait` on it is held, not read through; its first event is `tracked` with `merged` and `activity` carrying the 2 comments; a `manual` PR keeps its source (STA-5, STA-8, MOD-15, API-18). |
| `starting` | Before the first poll answers, `list` waits up to 10 s, then exits 9 with `starting` (API-18). |
| `head-moved` | A `checks-done --sha` wait whose head matched and then moved ends with `head_moved`, exit 4; one whose SHA never matches ends so at the first refresh 60 s after it began (API-11). |
| `rerun` | After a re-run on the same head, `--rerun-since <cursor>` doesn't hold on the previous run's result (API-10). |
| `waiter-limit` | A 65th waiter gets `limit`, exit 10; a client that closes frees its place (API-14). |
| `renamed` | The repository is renamed, with the same node ID: one record, `pr` takes the new name, one `edited` event naming `pr` (MOD-1). A wait held through the rename goes on; a read-through under the new name returns the same record. A transfer to an owner not in `owners` makes an `authored` PR `asked` (POL-4, POL-5). |
| `unlisted-values` | A check concluding `startup_failure`, or an unknown `FOO`, reads `failing`, and the record decodes (MOD-2, MOD-5). |
| `head-back` | A force-push back to the previous SHA within 20 s reads `checks_pending` until settled again (MOD-6). |
| `base-changed` | The base changes while `mergeable` reads `UNKNOWN`: the record reads `unknown` at once (MOD-8). |
| `gone-returns` | A gone PR returned open gets `reopened`, `settled` false and its retention clock cleared; returned merged, `merged` and the clock started again (MOD-11, STA-2). |
| `pr-error` | One PR's node is `null` with a `FORBIDDEN` error on every refresh. The other PRs are applied; it stays open and `stale` with `error.type` `FORBIDDEN`, and `show` prints `error FORBIDDEN`. After 5 minutes `pr_failing` is raised, naming the type; it never becomes `gone`; the first applied refresh clears both. A read-through meeting it answers `github_unavailable` naming the type (POL-16, POL-21, POL-24, API-5). |
| `many-prs` | 41 tracked PRs refresh in two requests; 150 open PRs are found over two pages. At 200, a `track`, a `show` of an untracked PR and a `wait` on one each get `limit`, exit 10, and nothing is sent; found PRs past the limit are left out, oldest `updated_at` first, with `pr_limit`, cleared once the finding fits (POL-7, STA-3). |
| `track-untrack` | A second `track` sends no request and makes no event, also at 200 PRs. `untrack` of an untracked PR sends no request and answers `record: null`; of an `authored` one changes nothing; of a `manual` one makes it `authored` if it's the user's own, open and its owner is in `owners`, and otherwise drops it with `untracked`, and with a waiter makes it `asked` while the wait goes on (API-15, API-9, STA-1, STA-3). |
| `forced` | Two `show --fresh` within 5 s send one refresh; the second is answered from memory. Two `refresh` within 10 s send one poll; the second is `shared`, cost 0. Three `show --fresh` arriving while one is in flight share it. At 200 PRs, a `show --fresh` arriving during a poll's first request is the next request the fake receives (POL-15, API-16). |
| `first-run` | No login: `status` answers at once, and `list` exits 7 at once naming `gh auth login`, not `starting`; after a login the next `list` answers within 5 s: it causes the token read (POL-20: before a request that needs GitHub, at most once in 5 s). A slow token read: requests that need GitHub wait for it, `status` doesn't. GitHub unreachable from the start: `list` exits 9 with `github_unavailable` and `until` once the first poll fails, not after 10 s. A periodic read that fails keeps the token; one that reports no login drops it (API-18, POL-3, POL-19, POL-20, OPS-5). |
| `restart-offline` | A daemon restarts with GitHub down: `list` exits 9 with `github_unavailable` (API-18), `status` counts its loaded PRs as tracked, and it idle-exits, writing the file. A restart with GitHub up finds every saved entry unchanged: a `manual` PR keeps its source, an ended one its state and saved time, and 2 comments made meanwhile arrive as `activity` (STA-5, STA-8). |
| `crash` | The daemon crashes mid-poll: the next start loads the last written file, replaces the stale socket, and a found PR whose first refresh wasn't applied is found again (STA-7, OPS-4, POL-4). |
| `files-removed` | The socket removed, or the lock file replaced, under a running daemon: within a minute it stops, and the next command starts a new one; a stopping daemon leaves a newer one's socket (STA-11). |
| `clock-back` | The wall clock steps back an hour: no ended PR is dropped early, a wait's deadline is unchanged, and the quota count isn't reset (POL-26, STA-2, POL-22). |
| `retention` | A merged PR is dropped at the first tick 24 h after it was seen, by the wall clock, with an `untracked` event, and `list --since` names it. With a waiter it stays until the waiter ends. With `keep_done` 0, a `merged` wait on it is satisfied before the drop. An `asked` PR leaves 60 minutes after its last request ended, never while waited on. A wall-clock jump of 8 days drops every ended PR at the first tick. A saved entry past `keep_done` is dropped on loading. A `show` of a dropped PR reads it through as `asked`, with no `activity` for old items (STA-1, STA-2, STA-5, STA-8). |

- **TST-9** **Real processes**, on Linux and macOS: on CI's runners once there is one (TST-14), and until then on Linux locally and on the owner's Mac: the CLI starts the daemon and returns while it lives on; two CLIs at once leave one daemon; a stale socket file is replaced; `stop` and `SIGTERM` leave no socket and a valid state file; the idle exit; a daemon older than the CLI is replaced and a waiting CLI reconnects to the new one; after a `stop` a waiting CLI starts none (CLI-7 to CLI-10, STA-11, OPS-7, OPS-8). Also: the CLI's stdout, read to its end, closes when the CLI exits while the daemon lives on; a spawned daemon uses gh's login although `GH_TOKEN` was set to a second marker, which the fake GitHub never receives; a bad config exits 6 within 1 s (CLI-7); the stop's 5 s deadline (OPS-7); a foreground daemon taking over a spawned one (OPS-6); `stop` on a daemon sent `SIGSTOP`, with the CLI's limit at 2 s (CLI-8); a log that can't be written (OPS-9); the token reader tells the fake `gh`'s outcomes apart and kills a `gh` that doesn't answer in 10 s (OPS-5); a socket path over 103 bytes is refused, and a regular file at the socket path stops the daemon, naming it (OPS-4); a daemon killed with `SIGKILL` while a CLI waits: the CLI starts none and ends `daemon stopped`, exit 6 (CLI-10); the state and runtime directories are 0700, an existing 0755 one becomes 0700, and the socket and `state.json` are 0600 (OPS-3, OPS-4, STA-7); with 200 tracked PRs on the fake GitHub, the daemon stays under 30 MB resident, and a `list` answered from memory returns within 50 ms (OPS-17); exit codes 130 and 143 (CLI-5).
  - **Every real-process test runs a test build** (TST-1) against the fake GitHub, with `HOME`, every XDG directory and `GH_CONFIG_DIR` in one temporary directory under a short root (`/tmp`, not macOS's `$TMPDIR`), so every path of OPS-3 and OPS-4 is its own and the socket path stays under 103 bytes, and `gh_path` set to a fake `gh` script that, as gh does, prints a non-empty `GH_TOKEN`, else `GITHUB_TOKEN`, else a marker token (docs/02 §1), or exits 1 with `no oauth token found for github.com`, or fails otherwise, or never exits. Its config sets `exit_after` to a few seconds. It fails after 30 s, and stops every daemon named in its `circitor.lock`, also when it fails.
- **TST-10** **The state file:** **its writes go through a file-system interface the harness can fake**: stopped after each step, or by a power cut that loses all that wasn't synced, a write leaves the old or the new file, never half of one. A write that fails (a full disk, a denied permission) is logged and retried, and the daemon keeps serving; at a stop it's logged and the exit is 0 (STA-7, OPS-7). A temporary file left by a crash doesn't stop the next start; a corrupt file is set aside, with `state_file_set_aside`; a file with a newer `version` is left unchanged and never written, with `state_file_newer`; no title or token is ever in it (STA-6 to STA-8). A change 2 s after a write is in the file 5 s after that write, with nothing else changing (STA-7). `testdata/state/` keeps one file per released `version`, with an unknown key added; each loads with every entry (STA-8).
- **TST-11** **Secrets.** **The token every test uses is a marker string** (TST-5, TST-9), and at its end each test searches the log, the state file, every API response and all CLI output for it (OPS-5). The fake `gh` also prints it on stderr, and before failing. The fake GitHub puts markers of its own in every title, every error `message` and the 401's body; none is ever in the log or the state file (OPS-9).
- **TST-12** **Fixtures.** `testdata/github/` holds real responses recorded from `yachiko/experiment`, with names, titles and IDs replaced. **One file per response**, a JSON object: the `request` it answers (circitor's own query), the HTTP `status`, the `headers` that matter (`date`, `retry-after`, `x-ratelimit-*`) and the `body`. Synthetic ones, written from docs/02, sit beside them under another directory until real ones exist. A test decodes each with the production code, so a field GitHub renames fails here first. They're recorded by a manual task. (proposal)
- **TST-15** **Derivations** are tested as tables over single records, with no fake GitHub: `checks.state` (MOD-5), a truncated list's state (MOD-7) and `status` (MOD-11), one case per row, and one per pair of adjacent `status` rows, whose order decides the word: a failing draft reads `checks_failing`, a conflict with failing checks `conflict`.

## By hand

- **TST-13** **The owner's acceptance checks**, on a Mac and, where a step says so, on Linux, on a release published to the tap and before it's announced. Results go into docs/05 on the owner's say:
  1. Install from the tap; `circitor list` starts the daemon and shows the open PRs: with `owners` empty and nothing tracked by hand, the same set as `gh search prs --author @me --state open --limit 200`, run a minute after the last PR opened or closed.
  2. In `yachiko/experiment`, under docs/05's rules, open a PR whose branch carries a workflow, push to it, and run `circitor wait --until checks-done --sha $(git rev-parse HEAD)`: it returns when the checks finish, with the right exit code. Close it unmerged: `circitor wait --until merged` exits 4 with `ended: closed`.
  3. Open a second PR there with one file and no workflow, and merge it: `circitor wait --until merged` returns.
  4. With no other `gh` use, run a watch loop for an hour, and compare the fall of GitHub's `rateLimit.remaining` within one reset window with the costs circitor logs under `CIRCITOR_LOG=debug`, give or take the counters' lag (docs/02 §2).
  5. The same commands from Claude Code, on macOS and on Linux, with its sandbox off, with `sandbox.excludedCommands`, and with `sandbox.network.allowUnixSockets` (OPS-14, docs/03 §6 item 1).
  6. The open items of docs/04 §8 the specs rest on: an unsigned binary from the tap runs on Apple Silicon (item 1); `circitor daemon` as OPS-18's LaunchAgent finds `gh` and gets a token (items 2, 4); a `wait` held across a lid close ends on waking as `timeout` if its deadline passed, on macOS and on Linux (item 6, POL-22).
- **TST-14** **CI** runs formatting, lints with warnings as errors, and every test on Linux and macOS. **Not set up for now** (the owner, 2026-11-25): `make verify` on each merge is the gate meanwhile. (proposal: the CI service)
